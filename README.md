# PortFlow AI — Container Congestion Predictor & Port Operations Optimiser

> **IBM Bobathon Track:** AI &nbsp;|&nbsp; **Problem:** L1 — Container Congestion Predictor & Port Operations Optimiser

---

## Problem

Port shift supervisors managing a single container terminal have no reliable way to anticipate berth congestion before vessels arrive.  Today they rely on spreadsheets and intuition, which means congestion warnings come too late to re-sequence berths or reallocate cranes before vessels are already queuing.  The result is unpredictable vessel waiting times, sub-optimal crane utilisation, and shift plans that are rebuilt manually for each duty window.

**Primary user:** A port shift supervisor responsible for one container terminal, working a 12-hour shift, who needs to understand the cause of a predicted risk, compare a baseline schedule with an optimised proposal, and explicitly approve or reject routing and plan changes.

---

## What Makes PortFlow AI Different

Most port-intelligence tools stop at a risk dashboard — they show a congestion probability but leave the supervisor to figure out what to do next.  PortFlow AI closes the full loop:

```
Vessel schedules + berth capacity
        │
        ▼
  [ML Model]  →  Congestion risk score + vessel waiting-time forecast
        │
        ▼
  [CP-SAT Solver]  →  Jointly optimised berth & crane assignments
        │
        ▼
  [72-hour Plan]  →  Shown to supervisor with explanation
        │
        ▼
  [Human Approval Gate]  →  Supervisor approves / rejects before any change takes effect
```

IBM Bob explains model outputs and plan summaries in plain language via a read-only MCP server.  **No LLM calculates assignments, invents numerical schedules, or approves consequential actions.**

---

## End-to-End Demo Outcome

A working demo will show a shift supervisor:

1. Viewing predicted congestion hotspots for the next 72 hours.
2. Seeing estimated vessel waiting times with a confidence range.
3. Reviewing alternate routing recommendations when net operational benefit is positive.
4. Inspecting an optimised berth and crane assignment plan generated by OR-Tools CP-SAT.
5. Reading a plain-language explanation produced by IBM Bob (MCP) — not an LLM schedule.
6. Explicitly approving the plan so it becomes the active shift schedule.

## Quick Start (once `src/` is implemented)

See [`docs/setup-guide.md`](docs/setup-guide.md) for full prerequisites, environment variables, and troubleshooting.

```bash
# Clone the repository (URL pending — see submission.yaml)
git clone <REPOSITORY_URL_PENDING>
cd bob-ai-hackathon-portflow-ai

# Backend
cd src/backend
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS/Linux
pip install -r requirements.txt
cp .env.example .env            # edit DATABASE_URL and SECRET_KEY
alembic upgrade head
uvicorn app.main:app --reload --port 8000

# Frontend (new terminal)
cd src/frontend
npm install
cp .env.example .env            # edit VITE_API_URL
npm run dev
```

Health check: `GET http://localhost:8000/health` → `{"status": "ok"}`

## IBM Bob Usage

IBM Bob is the primary development IDE for this project.  Key uses:

- Writing and reviewing FastAPI route handlers, Pydantic schemas, and SQLAlchemy models.
- Generating and verifying OR-Tools CP-SAT solver logic.
- Explaining model outputs and 72-hour plan summaries through a read-only PortFlow MCP server.
- Task histories and task-consumption screenshots are exported to `bob_sessions/`.

Bob does **not** calculate berth or crane assignments, generate numerical schedules, or approve operations plans.

## Data Policy

- All data used during development is reproducible, seed-driven synthetic data generated from documented assumptions.
- Synthetic records are clearly labelled in the database and in API responses.
- No confidential, personal, client, or social-media data is used.
- Any public dataset used will include a source/provenance record in `docs/DATA_DICTIONARY.md`.
